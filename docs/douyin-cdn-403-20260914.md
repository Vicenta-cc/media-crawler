# 抖音 CDN 403 修复与实测（2026-09-14）

## 结论

这次实测最有效的修改是媒体 GET 同时携带浏览器的 `User-Agent` 和 `Referer: https://www.douyin.com/`。三条相同入口 URL 的配对对照中，裸 GET 全部 403；同时带这两个请求头全部返回视频。旧直连 CDN 地址仍可能失效，一条历史失败地址补头后仍为 403，重新取同帖播放地址后为 200。因此不能只补头，也不需要每条下载前都额外刷新详情。

改动位于独立 worktree `MediaCrawler-cdn-reliability`，分支 `codex/douyin-cdn-reliability`，从正式运行的 MediaCrawler 提交 `d9aa0c10acdd6de8701303afe34a1c0f9cf2d42e` 创建。正式应用基线 `2134c7b`、正式 crawler、数据库、key、endpoint 和端口部署均未修改。

### 历史失败地址与新地址

对之前 15:35 日志中失败的帖子 `7651953212009794856`，在同一账号下测试：

1. 历史直连 CDN URL + UA/Referer：403。
2. 重新请求同帖详情，取得新播放地址 + 同样请求头：200，Content-Type 为 video/mp4，前缀为 MP4 文件头。

CDN 只返回通用 Forbidden，未给出足以区分过期、签名、访问控制的原因。本试验支持“旧地址失败时刷新地址有用”，不证明所有 403 都由过期引起。第二步只做前缀探测，不将它计入四条完整下载。证据：[历史地址对照](evidence/cdn-historical-20260914.json)。

## 已实现的处理

1. 媒体请求使用实际浏览器 UA 和抖音 Referer，并在重定向中保留。按白名单构建媒体请求头，不把 API 的 Host、Cookie、Authorization 复制到其他 CDN 域名。本次成功不依赖额外 CDN Cookie。
2. 视频候选列表保留原首选顺序，去重后可用备用地址；修复旧提取函数只有一个 URL 时误判“没有视频地址”的问题。
3. 默认先尝试最多两个地址；全部失败且遇到 403/410 时，仅刷新一次详情，再尝试最多两个新地址。默认最多四次媒体 GET、一次额外详情请求；成功立即结束，不对正常视频重复刷新详情。
4. 媒体 GET、备用尝试和刷新请求共用当前客户端的节流器，默认请求启动间隔五秒。429 停止该视频的重试，不尝试以备用地址放大请求。这个局部限速器不替代未来任务/账号之间共享的全局限速设计。
5. 空响应或 HTML/JSON/XML 错误页即使 HTTP 200 也不当成成功媒体保存。网络失败、候选耗尽和刷新超时有明确退出边界；取消信号继续向上传播。
6. CDN 失败与账号/API 验证错误分开；本改动不因 CDN 403 换号。失败日志记录源/最终主机、HTTP 状态和错误类型，不输出完整签名 URL。

配置位于 `config/dy_config.py`：

```python
DY_MEDIA_REQUEST_INTERVAL = 5.0
DY_MEDIA_MAX_URL_ATTEMPTS = 2
DY_MEDIA_REFRESH_ON_FAILURE = True
```

当前流式路径本来就是先下载媒体、再处理该帖评论；本次无需把评论顺序再改一次。后台批量保存旧 CDN 直链并过很久才下载仍然容易失败，建议持续使用“轮到该帖 → 当前播放入口下载 → 失败后有限刷新”的流程。
